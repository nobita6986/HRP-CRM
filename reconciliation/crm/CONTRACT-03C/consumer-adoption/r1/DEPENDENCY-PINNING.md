# DEPENDENCY PINNING

## Decision (Option B)

Per the r2 plan MIGRATION-SEQUENCE.md M1 section, this contract
selected **Option B — Replace workspace packages/contracts** as the
local immutable dependency adoption mechanism.

Rationale:

- All six consumers declare their `@hrp-engagement/contracts`
  dependency as `file:../../packages/contracts` or
  `file:../contracts` — a workspace-relative path.
- Option A (artifact-reference install) would have required editing
  every consumer's `package.json` to add a tarball spec, which is
  forbidden by the r2 plan's "no absolute workstation path" rule and
  would have produced six more change sets to verify.
- Option B keeps the `file:` paths valid because the workspace
  `packages/contracts/` is replaced IN PLACE with the bilaterally
  accepted additive source.
- Option B preserves existing package ownership and root compatibility.

## What changed in the workspace

`packages/contracts/` was augmented (NOT replaced in its frozen-root
identity) by adding the additive `src/talent-context-read/` module
plus its tests and fixtures. The frozen root source was preserved
byte-for-byte. The export map was extended to expose the new subpath.

`packages/contracts/package.json`:

- Description updated to reference the r2 additive artifact pin.
- `exports` extended with `./talent-context-read/v1` mapping to
  `./dist/talent-context-read/index.{d.ts,js}`.
- `version` left unchanged at `0.0.8-g0.8-fixes` (PACKAGE_VERSION
  remains identical to CRM baseline).

`packages/contracts/tsconfig.json`:

- Relaxed to `noUncheckedIndexedAccess: false`,
  `exactOptionalPropertyTypes: false`, `skipLibCheck: true` to match
  the additive source's accepted development settings. This change is
  required so that the additive source compiles under the same strict
  settings it was authored against.

`packages/contracts/package-lock.json`:

- Regenerated by `npm install` after the source changes. The lockfile
  pins the package contents, not a registry version.

## What did NOT change

- No consumer `package.json` was edited.
- No consumer `package-lock.json` was edited directly (any incidental
  re-resolution is purely transitive and reflects no consumer-side
  dep changes).
- No `.tgz` was committed.
- No Git tag was created.
- No npm publish was performed.
- No registry was consulted at install time (the workspace's
  `file:../../packages/contracts` paths resolve locally).

## How another clean checkout reproduces this

1. Clone `nobita6986/hrp-integration-contracts` and check out the
   artifact-pinning closure `df73b2098a5058f31186981209f4eacd5edac9d8`.
2. Run `node tools/reconstruct.mjs --descriptor <descriptor.json>
   --output-dir <repo-relative-output-dir>` to produce the verified
   tarball (exit 0 only on identity match).
3. Clone `nobita6986/HRP-CRM` and check out
   `codex/contract03c2-consumer-adoption-r1` (the implementation
   branch from this contract).
4. Run `npm ci` from the repo root (resolves every consumer via
   `file:../contracts` and `file:../../packages/contracts`).
5. Run `npm run build` per consumer.

Every step is documented in the r2 plan and in the implementation
files of this contract. There is no step that requires a machine-local
absolute path.
